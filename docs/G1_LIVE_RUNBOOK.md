# G1: передача для реальной проверки MAX

Статус: **NOT_VERIFIED / BLOCKED_BY_PREREQUISITES**. Этот файл — точные действия для уже разрешённого технического теста, не свидетельство выполненного deployment и не запрос создать инфраструктуру. `REAL_APPLICATION_SMOKE = REQUIRED`. Активный сеанс в каждом клиенте — не более 15 минут.

## 1. Подготовка существующего окружения

Ответственный указывает организаторского бота именно этого проекта (публичный nickname и подтверждённый bot ID), существующий согласованный host/domain и оператора. Закрыто сохраняет ссылку/документ выдачи, применимые условия сервисных сообщений и согласие тестировщиков. Уже достаточных условий организаторов достаточно; повторное разрешение не требуется. Наличие токена само по себе не доказывает эту область использования.

Секреты передаются через защищённые файлы `secrets/` или закрытое окружение на согласованном host, **не через чат, process arguments, Git или Docker build**. Для PEM, если его требует текущая цепочка MAX, сначала сверить официальный источник и SHA-256/fingerprint; затем подключить только read-only `NODE_EXTRA_CA_CERTS`. Не менять Windows trust store, TLS verification или firewall. Если этот путь не подготовлен, остановить только live-действия.

В `.env.live` задать APP_MODE=live, DATABASE_PATH=/app/runtime/probe.sqlite, MAX_EXPECTED_BOT_ID, PROBE_TESTER_IDS, PUBLIC_BASE_URL, LIVE_SCOPE_CONFIRMED=true. MAX_BOT_TOKEN_FILE и MAX_WEBHOOK_SECRET_FILE указывают файлы `/run/secrets/…`; при использовании `_FILE` удалить одноимённую прямую переменную. Для начала достаточно двух согласившихся тестировщиков, чтобы проверить чужую кнопку; это техническая роль, не исследовательская квота. Значения не публиковать.

Для public Compose в закрытом окружении процесса задать PUBLIC_HOST, ACME_EMAIL и SOURCE_VERSION (SHA-256 рассмотренного source manifest). Никакого домена по умолчанию нет. Применить тот же рассмотренный Dockerfile/образ, отдельный live volume. Не переносить синтетическую local SQLite в live: приложение отклоняет смену mode/bot identity.

Подготовка на **уже согласованном host**:

```sh
docker compose -f deploy/compose.public.yaml build app
docker compose -f deploy/compose.public.yaml run --rm --no-deps app node dist/scripts/live-admin.js inspect
```

`inspect` вызывает только GET /me и GET /subscriptions. Проверяет ожидаемый bot ID/is_bot и схему ответа; печатает только количество подписок и совпадение designated endpoint. Полные URL чужих подписок не выводятся, поскольку могут содержать секрет. Ответственный проверяет существующее владение/доставку в закрытом контексте; совпадение URL не равно доказательству эксклюзивного consumer.

Этот одноразовый контейнер не запускает HTTP-сервер/worker и не принимает события. Только после проверки владения и отсутствия другого consumer запустить `docker compose -f deploy/compose.public.yaml up -d`.

## 2. Подписка и проверка ingress

Обычный startup не меняет подписку. Не запускать Long Polling. До отдельного `subscribe` подтвердить отсутствие другого worker/consumer, установить `LIVE_EXCLUSIVE_CONSUMER_CONFIRMED=true` в закрытом `.env.live` и применить env к контейнеру.

Если список подписок пуст и designated endpoint доступен по доверенному HTTPS:443:

```sh
docker compose -f deploy/compose.public.yaml exec -T app node dist/scripts/live-admin.js subscribe
```

Скрипт снова проверяет /me и subscriptions, затем выполняет один POST /subscriptions и проверяет success:true и фактический список. Подписывается на шесть lifecycle типов, message_created и message_callback. **Реальное входящее событие проверяется отдельно**. При timeout результат неоднозначен: сначала повторить `inspect`, а не POST.

При любой существующей подписке автоматическая замена запрещена, даже при совпадающем URL. Чужой endpoint/неясное владение/замена secret требуют конкретного решения о designated endpoint; скрипт завершится с понятным кодом и ничего не удалит. Не пытаться «починить» это вторым consumer.

HTTP 200/success:false, malformed, 401, 429 и timeout имеют отдельные причины ошибок; они не подтверждают рабочую подписку. После новой валидной конфигурации и проверки /me/своей подписки оператор может явно выполнить `live-admin.js clear-auth-block`. Это снимает техническую блокировку **новых** отправок; старые исходящие операции не воспроизводятся.

## 3. Сеанс mobile/web

Для каждого клиента записать дату, ОС/версию приложения или браузера, роль A/B, SOURCE_VERSION/image ID. Рабочие токены, сырые events, личные ID и необработанные скриншоты — только `docs/private/` либо другое исключённое место. В публичном протоколе — обезличенная роль, ожидание, фактический результат и путь безопасного свидетельства. Не подделывать события клиента.

| Шаг | Действие человека и ожидаемое поведение | Mobile | Web |
|---|---|---|---|
| G1-M01 | A открывает `https://max.ru/<выданный_nickname>?start=g1`, запускает бота; видит «Технический тест G1» и кнопку | NOT_VERIFIED | NOT_VERIFIED |
| G1-M02 | A повторно открывает deep link; записать, приходит ли bot_started. Если нет — `/probe` восстанавливает путь; не приписывать событие платформе | NOT_VERIFIED | NOT_VERIFIED |
| G1-M03 | A нажимает кнопку; ожидается callback-ответ и отдельный вопрос. Отдельно сверить HTTP ack, inbox result и результат MAX; затем факт видимого сообщения | NOT_VERIFIED | NOT_VERIFIED |
| G1-M04 | Сначала A пишет «готово» обычным сообщением: получает инструкцию «Ответить». Затем использует естественное действие клиента «Ответить» на вопрос и пишет «готово»: тест завершён | NOT_VERIFIED | NOT_VERIFIED |
| G1-M05 | Записать, нашёл ли A действие reply самостоятельно, сколько действий потребовалось и помогла ли инструкция. Проверить фактический `message.link.type=reply` и `message.link.message.mid` в закрытом контексте без raw dump | NOT_VERIFIED | NOT_VERIFIED |
| G1-M06 | Повторить нажатие старой кнопки; начать новый probe, затем нажать предыдущую. Для expiry сделать новый отдельный короткий сеанс после срока либо согласованный TTL=60 сек; старые команды не исполняются | NOT_VERIFIED | NOT_VERIFIED |

Если question mid не подтверждён MAX (неоднозначная отправка/timeout), произвольный ответ не привязывать. После устранения проблемы A начинает новый `/probe`. Если в клиенте отсутствует документированный reply-контекст, записать ограничение и оставить пригодность механизма NOT_VERIFIED; UI-фреймворк/mini-app не добавлять автоматически.

## 4. Отчёт и завершение сеанса

Для каждого шага: expected/actual, client version, code/source manifest, время, обезличенное evidence, статус PASS/FAIL/NOT_VERIFIED. Отдельные поля: `webhook_ack`, `processing_result`, `max_request_result`, `human_observation`. Не суммировать их в один недоказанный «доставлено».

Остановка сеанса не является отпиской бота: действующую чужую или проектную подписку не удалять без поручения. Согласованный оператор сохраняет доступ в пределах подтверждённого периода и следит за истечением/очисткой technical data. Для технического PASS нужны оба реальных клиента и измеренная Docker-сборка. Продуктовый T14 требует полного будущего сценария и этим протоколом не закрывается. После свидетельств — G1 review; G2 требует отдельного явного одобрения продукта/риска/объёма.
