## Что действительно имеется

Архитектурная основа остаётся одна: TypeScript/Fastify, один worker, SQLite, HTTP-адаптер MAX, Docker. Обследованы все 8 файлов `src`, конфигурация, Docker inputs, scripts и существующие тесты. Переименование продукта не требует удаления или переписывания этого основания.

| Часть | Фактическое состояние и пригодность |
|---|---|
| `src/app.ts`, `index.ts` | Реальные `/healthz`, `/webhooks/max`, проверка secret до разбора, предел 64 KiB, graceful shutdown. Полезно повторно использовать. Сейчас принимаются только allowlisted тестировщики |
| `contracts.ts` | Lossless int64, валидация входа, дедупликационные ключи и нормализация без raw events. Общие контракты пригодны. Разбор `/probe`, «готово», payload `g1:` и exact reply — только probe; их нужно отдельно адаптировать под диалог выбора |
| `max.ts` | Разделены local simulation и live transport; таймаут/предел ответа, проверка получателя и semantic success, без отключения TLS. Тип клавиатуры сейчас содержит только callback; внешняя link-кнопка потребует будущей контрактной адаптации |

## Внешние предпосылки, риски и следующий шаг

Для реализации нужно решение пользователя о продукте/городе/объёме и доступных часах. Для рабочего обновления выбранного открытого набора — выданный ключ или малый актуальный экспорт, проверка целевой выборки и ответственный за сверку; права на открытые факты уже установлены в 04. Подготовленный режим — отдельный явно обозначенный fallback. Для live MAX — подтверждённый организаторский бот, применимые условия сообщений, безопасно размещённые credentials, существующий согласованный HTTPS-host/оператор и тестировщики с двумя клиентами. Всё это нельзя вывести из успешного локального теста. Токены/пароли/сырые персональные данные в чате не нужны.

Недоступность live MAX не блокирует подготовку нормализации, диалога, контрактов и пользовательских заданий после разрешения соответствующего этапа. Не закрытые права на один API не блокируют проверку другого разрешённого источника. Блокировка push также не блокирует документы. До выполнения внешних условий реальные сообщения, subscription changes и deployment не выполняются.

Основные риски: устаревшие/неполные данные и неясные права; недостаточная ценность по сравнению с афишами; договорные ограничения уведомлений; probe-specific связывание transport/domain; отсутствие реальных клиентов/host.
