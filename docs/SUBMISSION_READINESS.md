## Продукт и реализованный путь

«Культурный план» помогает взрослому жителю Казани выбрать одно культурное занятие по дате, времени и бюджету на вход. Пользователь задаёт условия, при желании выбирает интерес, смотрит до трёх совпадений по известным данным. Отдельная кнопка открывает до трёх вариантов с неизвестными условиями. Интерес влияет на порядок, обязательные ограничения не расширяются. Карточка показывает место, часы или сеанс, последний вход, применимую цену, регистрацию и источник. Событие можно сохранить, открыть и удалить из личного списка; `/delete_data` очищает закладки и параметры. Сохранение не означает регистрацию или покупку билета.

Сценарий реализован в существующем боте: HTTP → durable inbox → worker → SQLite → renderer → транспорт MAX. Локальные примеры полностью вымышлены. Актуальная доступность реальных событий, востребованность и выигрыш во времени не доказаны. [Продуктовое решение](pivot/01_PRODUCT_DECISION.md) и [пять этапов](pivot/03_IMPLEMENTATION_PLAN.md) остаются действующими документами.

### A: точный инженерный остаток после выбора

Текущий `--synthetic-current` ([генератор](../scripts/prepare-flow-fixture.ts), [fixture](../src/culture/fixture.ts)) создаёт новый вымышленный снимок по фактическим часам. [Polling loader](../src/polling-config.ts) и [preflight](../scripts/live-preflight.ts) требуют возраст около часа, [selector](../src/data/select.ts) проверяет давность фактов 24 часа, [закладки](../src/culture/flow.ts) — ещё и окончание выбранного посещения. **30 минут / 120 запросов — бюджет клиентской кампании, не политика доступности сдачи.** Просто оставить процесс или обновлять retrievedAt нельзя.

Предлагаемая стратегия для утверждения — **фиксированный вымышленный набор на весь период оценки**, без ежедневной операторской регенерации:

1. После получения дат создать отдельный versioned manifest и JSON: явно fictional, generatedAt — фактическое время создания, evaluationStart/evaluationEnd, validUntil, hash и версия генератора. Покрыть допустимые запросы каждой даты оценки, включая «Завтра» и разрешённые пользовательские даты до +30 дней. Часы/правила посещения моделируются явно; диапазон дат не заменяет сеансы. Размер и границы набора проверяются до выпуска.
2. В `src/config.ts`, `src/culture/catalog.ts`, `src/data/select.ts`, `scripts/live-preflight.ts` добавить узкую проверяемую политику **только для versioned fictional release dataset**: срок действия manifest вместо свежести реального источника. Существующие test-polling ограничения оставить тестовыми; реальные 24-часовые проверки не ослаблять. Конкретное имя новой настройки пока не является поддерживаемой переменной. `FLOW_TEST_CLOCK` для live не включать.
3. В `src/culture/flow.ts` / `card.ts` показывать режим, версию, созданный набор и срок; убрать применительно к вымыслу утверждения о свежести источника. После expiry новый подбор сообщает об окончании демонстрационного периода; сохранённое открывается как истёкшая вымышленная закладка и удаляется. При корректном, но истёкшем manifest сервер после restart обслуживает это ограниченное поведение; готовность подбора отрицательная и видна оператору отдельно от исправности HTTP. Повреждённый/неверный hash не даёт fallback или выдачи. Restart не генерирует события автоматически и не сбрасывает SQLite.
4. Зафиксировать `eventId`/`occurrenceId`: сейчас identity = digest этой пары в `src/culture/card.ts`, удаление защищено generation. Для выбранного неизменяемого набора ID, факты и hash сохраняются при restart. Если позднее разрешат регенерацию, это новый явно synthetic version: неизменное посещение сохраняет ID, изменённая дата/сеанс получает новый ID; старую закладку нельзя переносить молча или превращать в другое событие. Версия снимка отделяется от identity посещения, старые действия остаются fenced.
5. Связать selected source SHA/image, manifest/hash, read-only mount и persistent volume в существующем Compose; обновить README/PDF/«О данных». Добавить только проверки срока/границ дат, restart, стабильных bookmarks, маркировки и отсутствия влияния на real guards. Проверить крайние даты периода и обычный путь проверяющего без ручной помощи. Финальный clean benchmark выполнить отдельно на выбранной версии.

Это **подготовленный перечень**, не выполненный release-mode код. Новый ingest сейчас не нужен. Применимые проверки затронутого кода обязательны после реализации; нынешние исторические PASS их не заменяют.

Будущее минимальное изменение после отдельного выбора B: добавить **разрешение для одного конкретного источника/набора**, привязанное к версии, допустимым записям/полям, сроку, основанию показа и атрибуции. Отдельная выбранная конфигурация webhook/Compose должна принимать подготовленный real-снимок с этим разрешением; test-polling не превращается в production.

До этого нужны: исходные достаточные цена для взрослого/часы или сеанс/адрес/допуск/регистрация, устойчивые event/occurrence ID, source/version/freshness, разрешение противоречий и применимые display terms. Для подготовленного каталога требуется политика фактической повторной проверки/истечения на весь срок оценки; для live — разрешённое обновление с честным отказом. У нового источника при необходимости меняется только его нормализатор/допустимые домены/контрактные проверки. Регрессии должны подтвердить отказ другим источникам, истёкшему разрешению, спорной записи и недостоверному strict. Новый источник, ключи и загрузки здесь не исследуются. **DATA_SUITABILITY=EXPLORATORY_ONLY; PUBLIC_DISPLAY=NOT_CLEARED** остаются.

## Передача размещения и доступа проверяющих

Один экземпляр Node **22.23.2 / Fastify**, SQLite на постоянном диске, один consumer, HTTPS webhook. Это подготовка передачи, **PUBLIC_DEPLOYMENT=NOT_VERIFIED / NOT_DEPLOYED; WEBHOOK_INGRESS=NOT_VERIFIED**. Наличие `deploy/compose.public.yaml` и `deploy/Caddyfile` не означает развёрнутую службу.

На 24.09.2026 официальные [GET /updates](https://dev.max.ru/docs-api/methods/GET/updates) разрешают polling для разработки/тестирования без webhook и требуют webhook для production; [POST /subscriptions](https://dev.max.ru/docs-api/methods/POST/subscriptions) требует HTTPS:443 с полной доверенной цепочкой и совпадением hostname с CN/SAN, без самоподписного сертификата; endpoint должен отвечать HTTP 200 не позднее 30 секунд. При активной подписке polling не работает. Приложение использует `X-Max-Bot-Api-Secret`; исходящие запросы — `platform-api2.max.ru` с сохранённым credential и проверенным process-scoped CA при необходимости. Проверка cutover включает быструю durable запись входа/ACK отдельно от последующей worker-обработки и чтения человеком; один health не доказывает доставку.

Бесплатный тариф без проверки persistent disk, sleeping, TLS, сети и нужного срока не рекомендуется. Существующий Compose использует Caddy с портами 80/443 и собственным сертификатом: host должен поддержать именно этот вариант. Если approved provider hostname имеет управляемый TLS/ingress, потребуется ограниченная адаптация proxy/Compose под его контракт с закрытым upstream Fastify; пригодность пока не установлена. DNS/firewall, ресурсы и сертификаты этой задачей не создаются. Реквизиты/политика пользователя, хранение и удаление, backups/RPO/RTO остаются входами оператора, а не обещанными свойствами host.

**Доступ проверяющего:** заранее согласовать именной приватный allowlist и получить отдельное согласие аккаунтов. Текущий webhook читает `PROBE_TESTER_IDS` (1–20 ID) из конфигурации; polling pairing хранит отдельный ignored `testers.json` и автоматически туда его не переносит. Оператор переносит только проверенные согласованные ID в закрытую конфигурацию выбранного выпуска, до начала оценки проверяет вход со своего допускаемого аккаунта и отказ неизвестному. Проверяющий получает ссылку [бота](https://max.ru/t432_hakaton_max_bot), период и краткую инструкцию `/start`; bot token и webhook secret ему не нужны. После однократного допуска обычные подбор/save/delete не требуют оператора. Если состав заранее неизвестен или больше 20, до выпуска нужен отдельно согласованный ограниченный механизм приглашения и небольшой кодовый шаг; открытый доступ всем молча не включается. Тестовые/административные реквизиты служебного пакета передаются только по согласованному закрытому каналу, отдельно от клиентского доступа.

Будущий cutover после выбора режима, реализации и разрешения размещения:

1. Остановить только принадлежащий задаче test poller, подтвердить exit/освобождение lock и сохранить test DB/cursor. Повторить identity/subscriptions. Чужую либо неясную подписку не удалять; конфликт остановит cutover.
2. Развернуть закреплённые source/image/dataset на approved host, один app и persistent SQLite. Webhook получает собственную DB identity; test polling DB и marker в webhook не копируются. Секреты — read-only mounts; non-root и текущие guards сохранены.
3. Проверить выбранные HTTPS origin/сертификат, `/healthz`, совпадение версии и writable persistent volume. Полный `compose config` с реквизитами не публиковать. Эти проверки ещё не выполнены.
4. Один раз зарегистрировать назначенный `/webhooks/max` через имеющийся `live-admin subscribe`, только при отсутствии подписки. При неоднозначном POST сохранить journal и выполнить GET reconciliation; не повторять POST и не менять путь журнала для обхода. Существующий правильный endpoint сверить, не регистрировать заново.
5. Наблюдать новое настоящее входящее действие допущенного проверяющего, durable обработку и ответ; выполнить mobile/web путь выбранного release mode. Проверить доступность и сохранение состояния после restart. Пропусков при переключении не исключаем: lossless cutover не установлен, полагаться на перенос marker нельзя.

## Что именно требуется для DATA-API.yaml

В предоставленной матрице (PDF 10, C05) перечислены девять групп: версия схемы конфигурации; решение/команда; базовый HTTPS-адрес; обязательные проверки; HTTP-метод и относительный путь; query/path/headers/body; роль; ожидаемые статусы; тип/структура ответа с обязательными полями. Отдельный официальный schema-файл или шаблон не предоставлен. Это не препятствует подготовке содержимого.

[Черновик YAML](examples/DATA-API.draft.yaml) уже описывает оба имеющихся endpoint и ссылается на точные схемы OpenAPI. Имена YAML-ключей — локальный формат черновика, не объявленная схема организаторов. Неизвестные версия схемы, команда и HTTPS origin явно `null`; номера и реквизиты не придуманы. Перед сдачей заполнить подтверждённые значения, проверить допустимый формат и соответствие runtime, выпустить итоговый `DATA-API.yaml`. Отсутствие отдельного внешнего schema-файла само по себе не блокирует остальную подготовку.

## Короткая демонстрация

1. Объявить: технический тест на вымышленных событиях; данные провайдера пользователям не отправляются. Записать code/image и версии клиентов. Для локальной демонстрации: `node dist/scripts/readiness-walkthrough.js`; вывод создаётся renderer, MAX симулирован.
2. `/start` → Подобрать → Другая дата → Назад → Завтра → время → бюджет 500 ₽ → Театр. Показать две категории, театр первым и отдельную группу совпадений.
3. Открыть детали: адрес, 10–18, последний вход 17:30, взрослый билет 200 ₽, обязательная регистрация. «Все условия» раскрывает отдельные сведения/наблюдения. Изменить фильтр и показать сброс opt-in.
4. Явно включить кандидатов: мастерская остаётся вариантом с неизвестным взрослым тарифом, при известном пересечении 12–18. Кнопки внешних ссылок помечены как примеры; доступность страницы не обещается.
5. Сохранить → список → другой клиент того же аккаунта → открыть → удалить → сохранить снова → restart test app → открыть → `/delete_data`. Второй согласившийся аккаунт отдельно проверяет изоляцию. Только фактические действия MAX считаются наблюдениями.

Для оставшихся реальных наблюдений действует замороженная матрица 12/13 и [очередь одиночных действий runbook](EXPLORATORY_MAX_RUNBOOK.md), по умолчанию 15 минут, явно запрошенное новое окно — до 30 минут; в обоих случаях ≤120 polling requests. Записать ограничения недоступных действий; нельзя подставлять локальный PASS вместо клиента.

Содержание будущего PDF: (1) закрытый служебный слайд по R12; (2) пользователь/задача и альтернативы; (3) короткий путь и неизвестные условия; (4) демонстрация с маркировкой данных; (5) устройство и измеренные проверки; (6) происхождение данных, приватность и ограничения; (7) проверяемые гипотезы, эксплуатация и следующий шаг. Партнёрства, подтверждённые эффекты и сроки отсутствуют. Публичный PDF не содержит секретов. Формат закрытого канала и возможный эквивалент служебного слайда согласовываются с организаторами по [00.5](00_REQUIREMENTS_AND_EVIDENCE.md#005-секреты-на-служебном-слайде).
